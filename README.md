"""# Banking Fraud Detection – Demo Dashboard

## Problem statement

The **Banking Fraud Hackathon** explores how to detect fraudulent credit‑card
transactions using a *lightweight* two‑stage model:

1. **Primary detector** – an XGBoost classifier trained on the classic
   transaction features (`Time`, `V1`‑`V28`, `Amount`).
2. **Secondary detector** – an Isolation Forest anomaly model that provides an
   additional signal for **review** decisions.

The goal of the demo is **not** to produce a production‑grade risk engine. It
showcases the trained models, a simple risk‑policy, and a Streamlit UI that
allows users to:
- inspect a single transaction,
- explore a few representative demo transactions,
- upload a CSV for batch scoring, and
- view a concise model / dataset summary.

All thresholds are **DEMO / REFERENCE POLICY** only – they are deliberately
conservative and must not be interpreted as production settings.

## Dataset facts

| Item                              | Value |
|-----------------------------------|-------|
| Training rows                     | 199,364 |
| Fraud cases (`Class = 1`)         | 344 |
| Fraud rate                        | ~0.1725 % |
| Features (input columns)          | `Time`, `Amount`, `V1`‑`V28` |
| No SMOTE, no temporal‑density signal |

## Methodology & model comparison

| Model                     | OOF PR‑AUC | OOF ROC‑AUC |
|---------------------------|-----------|------------|
| Logistic regression       | ~0.7334   | – |
| XGBoost (primary)        | **0.8473**| **0.9801** |
| Isolation Forest (secondary) | **0.1534**| 0.9379 |
| Temporal density (tested) | ~0.0015   | – |

The evaluation used **stratified 5‑fold cross‑validation**. Because the
dataset is extremely imbalanced, PR‑AUC is the primary metric; overall
accuracy is not informative.

## Final architecture (demo)

```
Transaction
   ↓
XGBoost fraud probability
   ↓
Demo risk policy
   ├── LOW      → APPROVE
   ├── MEDIUM   → REVIEW
   ├── HIGH     → REVIEW
   └── CRITICAL → BLOCK
               +
        Isolation Forest (secondary anomaly signal)
```

The Isolation Forest does **not** modify the XGBoost probability; it is used only
as a secondary signal when the primary probability falls into the **MEDIUM**
band.

## Limitations & important statements

- The dashboard is a **demonstration only**; thresholds are labelled as
  *DEMO / REFERENCE POLICY* and must not be used for real‑world decision‑making.
- The anonymised `V1`‑`V28` features have **no semantic interpretation** – they
  are PCA components supplied by the original Kaggle credit‑card dataset.
- No additional customer, merchant, geography, or demographic metadata is

- Temporal density was evaluated (see Phase 3) and **excluded** from the final

- No SMOTE or other synthetic‑sampling technique is applied.
- The UI performs basic validation; unexpected inputs will generate clear
  error messages.
